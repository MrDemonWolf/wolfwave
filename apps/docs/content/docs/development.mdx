**TL;DR:** clone the repo, copy `Config.xcconfig`, run `make build` and `make test`, then open a PR.
This page is for contributors. Just want to use the app? See [Installation](/docs/installation).

## The path

1. [Check the prerequisites](#prerequisites).
2. [Clone the repo](#clone-the-repo).
3. [Add your API keys](#configure-api-keys) in `Config.xcconfig`.
4. [Build and run](#build-and-run) the Debug app.
5. [Run the tests](#testing) and the [lint gates](#lint-gates).
6. [Open a pull request](#open-a-pull-request).

## Prerequisites

- **macOS 26.0+** (Tahoe) on **Apple Silicon** (M1 or later).
- **Xcode 26+**, with Command Line Tools (`xcode-select --install`).
- **Docker Desktop**, only for `make lint`, `make lint-baseline`, and `make lint-crash-safety` (they run a SwiftLint image pinned in the `Makefile`).
- **Node**, only for `make lint-headers` and `make lint-sync`. CI pins its Node version in `test.yml`.
- **bun**, only if you touch the docs site, OBS widget, Stream Deck plugin, or design tokens, or run `make widget`, `make icons`, or `make check-drift`.
  - Install exactly the version in the root `package.json` `packageManager` field.
  - Other bun releases minify the widget differently, so CI's drift check fails.

Only editing Swift? You don't need bun. Xcode ships the committed `widget.html` as-is.

## Clone the repo

```bash
git clone https://github.com/MrDemonWolf/wolfwave.git
cd wolfwave
```

Touching web code too? Install the bun version from the [prerequisites](#prerequisites), then install the workspaces:

```bash
bun install --frozen-lockfile
```

`--frozen-lockfile` keeps `bun.lock` unchanged. Don't commit lockfile churn.
`make widget`, `make icons`, and `bun run tokens` all run whichever `bun` is on your `PATH`, not a pinned copy. A different version can minify `widget.html` differently, which fails CI's drift check.

## Configure API keys

Copy the example config:

```bash
cp apps/native/WolfWave/Config.xcconfig.example apps/native/WolfWave/Config.xcconfig
```

Then fill in the two required keys:

```ini
TWITCH_CLIENT_ID = your_twitch_client_id_here
DISCORD_CLIENT_ID = your_discord_application_id_here
```

The copied file also sets `GITHUB_REPO_OWNER = your_github_username`. Set it to your fork, or delete that line.
Left as is, the app's GitHub, Releases, and Report a Bug links point at `your_github_username/wolfwave`.

- **Twitch Client ID:** create an app at [dev.twitch.tv/console/apps](https://dev.twitch.tv/console/apps).
- **Discord Application ID:** create an app at [discord.com/developers/applications](https://discord.com/developers/applications).
- **Discord art assets:** upload `apple_music`, `pause`, and `wolfwave` to your Discord app. See [Rich Presence art assets](#rich-presence-art-assets-fork-maintainers).

<Callout type="warn">
  `Config.xcconfig` is gitignored. Every contributor uses their own. Never commit it.
</Callout>

### Optional keys

| Key | What it sets | Default when blank |
|---|---|---|
| `GITHUB_REPO_OWNER` / `GITHUB_REPO_NAME` | Repo behind the GitHub, Releases, and Report a Bug links | Upstream repo |
| `DOCS_URL` | Docs site root (privacy, terms, changelog links derive from it) | Upstream docs |
| `COMMUNITY_DISCORD_URL` | Tray menu **Community Discord** link | Upstream invite |
| `COPYRIGHT_HOLDER` | Legal name in the About pane and on the setup completion screen | `MrDemonWolf, Inc.` |

<Callout type="warn">
  Escape `//` in URL values with `$()`, like `DOCS_URL = https:/$()/example.com`.
  xcconfig reads a bare `//` as a comment and silently cuts the value to `https:`.
</Callout>

Each optional value resolves in this order. A blank or missing value falls through to the next step:

1. **The key in `Config.xcconfig`.** Xcode expands it into `Info.plist` at build time. CI writes its own copy of this file.
2. **An environment variable** of the same name, read from the app's process.
3. **`Core/AppConstants`.** The default built into the app.

To rename the app itself, set `PRODUCT_NAME` and `INFOPLIST_KEY_CFBundleDisplayName` in the build configuration.
Keep the Debug and Release names different.

## Build and run

```bash
make open-xcode
```

Press **⌘R** in Xcode. Or build from the terminal with `make build`.

- Debug builds are a separate app: **WolfWave Dev** (`com.mrdemonwolf.wolfwave.dev`), with a `DEV` badge on its icon.
- It lives beside a real WolfWave install without touching its settings or Keychain.
- `make clean-dev` resets WolfWave Dev to a fresh first run. It never touches the production app.

<Callout type="info">
  Using a git worktree? `Config.xcconfig` is gitignored, so a new worktree has none. Copy `apps/native/WolfWave/Config.xcconfig` from your main checkout before you build.
  Run `bun install` once there if you'll touch web code.
  Each worktree builds into its own Xcode DerivedData folder, so check which `WolfWave Dev.app` you're looking at.
</Callout>

### Make targets

| Command | What it does |
|---|---|
| `make build` | Debug build |
| `make clean` | Clean build artifacts |
| `make clean-dev` | Quit WolfWave Dev, wipe its settings and Keychain entry, run `make clean`, then delete `/Applications/WolfWave Dev.app` and every `WolfWave-*` Xcode DerivedData folder (other checkouts and worktrees too) |
| `make test` | Unit tests (XCTest + Swift Testing) |
| `make test-verbose` | Unit tests with full `xcodebuild` output |
| `make test-ui` | XCUITest suite (launches the real app). See [UI tests](#ui-tests) |
| `make test-ci` | Unit tests the way CI runs them (unsigned, one at a time), writes `TestResults.xcresult` |
| `make ci` | Alias for `make test-ci` |
| `make lint` | SwiftLint against the tracked baseline (needs Docker) |
| `make lint-baseline` | Regenerate the baseline. It may only shrink (needs Docker) |
| `make lint-crash-safety` | No new force unwrap, `try!`, or `as!` (needs Docker) |
| `make lint-headers` | Swift file-header convention (needs Node) |
| `make lint-sync` | Source-derived lists, component catalog, docs values (incl. ports), lint claims, release-notes and version script tests (needs Node) |
| `make widget` | Rebuild the OBS widget into `Resources/widget.html` (needs bun) |
| `make icons` | Regenerate the Debug app icon from `AppIcon.icon` (needs bun) |
| `make sponsor-config` | Regenerate `SponsorConfig.generated.swift` from `FUNDING.yml` |
| `make check-drift` | Regenerate widget, tokens, SponsorConfig, and Debug icon; fail on drift (needs bun) |
| `make update-deps` | Resolve SwiftPM dependencies |
| `make open-xcode` | Open the Xcode project |
| `make prod-build` | Release build + DMG in `builds/`. Builds Apple Silicon (`arm64`) only |
| `make prod-install` | Release build + install to `/Applications` |
| `make notarize` | Sign, notarize, and staple the DMG (needs Developer ID) |
| `make verify-notarize` | Check the DMG's stapled ticket and Gatekeeper acceptance |

`make build`, every `make test*` target, and `make prod-build` run `sponsor-config` first, so you rarely call it yourself.

## Testing

Run `make test` (or **⌘U** in Xcode). `make test` prints one summary line: total tests, failures, and how many came from Swift Testing, like `N tests, 0 failures (M via Swift Testing)`.
Any failure also lists the failing tests and exits non-zero.
If the build itself fails, `make test` only says `error: no test results found`. Run `make test-verbose` to see why.

- **Unit tests** live in [`apps/native/WolfWaveTests/`](https://github.com/MrDemonWolf/wolfwave/tree/main/apps/native/WolfWaveTests).
- **New test file?** Drop a `.swift` file in that folder and `@testable import WolfWave`. No Xcode project edit needed.
- **Your real data is safe.** Tests use a throwaway settings suite and an in-memory Keychain. Never use `UserDefaults.standard` in a test.
- **Isolated output.** `make test*` builds into the gitignored `DerivedData/Tests`, so a test build never replaces the signed Debug app Xcode installs.

The rules for shared test state (the `SharedTestStateIsolation` lock, `WolfWaveTestCase`) are in the repo's [`CLAUDE.md`](https://github.com/MrDemonWolf/wolfwave/blob/main/CLAUDE.md#writing-tests).

### UI tests

`make test-ui` runs `WolfWaveUITests`. It launches the real app and drives it:

- the onboarding wizard, end to end;
- every settings pane, with a screenshot of each attached to the result.

The app runs with `WOLFWAVE_UI_TEST=1`, which swaps in throwaway settings and Keychain storage and keeps Apple Music, Twitch, Discord, and Sparkle off.
UI tests run as their own CI job and never gate a release.

Before the first run:

- Allow **Xcode Helper** to control your Mac under **System Settings → Privacy & Security → Accessibility**. macOS may label that pane **Device Control and Data Access**.
- Have an Apple Development or Developer ID Application signing identity. With neither, the run falls back to ad hoc signing, and macOS may refuse to launch the test build.
- Quit any running WolfWave Dev. `make test-ui` checks first (`scripts/check-ui-test-preflight.sh`) and stops if a copy is paused in a debugger. A copy that is only running gets a warning. `WOLFWAVE_SKIP_UI_PREFLIGHT=1` skips the check.

Details: [`apps/native/docs/end-to-end-testing.md`](https://github.com/MrDemonWolf/wolfwave/blob/main/apps/native/docs/end-to-end-testing.md).

### Web workspace tests

```bash
bun run --filter widget test           # OBS widget (bun test + happy-dom)
bun run --filter streamdeck typecheck  # Stream Deck plugin types
bun run --filter streamdeck test       # Stream Deck plugin
bun run ds:test                        # design-system lint rules and contrast guards
```

The docs site has its own checks. Run them in this order, because the SEO test reads the built `out/` folder:

```bash
bun run --filter docs types:check
bun run --filter docs lint
bun run build --filter docs
bun run --filter docs test             # unit tests plus the SEO guard
```

Preview the site with `bun run dev --filter docs`.

## Lint gates

Run these before you push. CI runs the same ones.

```bash
make lint                # SwiftLint against the tracked baseline
make lint-crash-safety   # Blocking: no new force unwrap, try!, or as!
make lint-headers        # Blocking: Swift file headers match the Xcode template
make lint-sync           # Blocking: source, catalog, and docs stay in sync
bun run ds:test          # Pins the design-system lint rules and contrast guards
bun run ds:lint          # Blocking: no literal font sizes, spacing, padding, radius, animation durations, or status colors in views
bun run ds:schema        # Validate tokens.json against its schema
```

`make lint-sync` also reads the docs pages. A page that names a WebSocket or widget port other than the `AppConstants` defaults fails it.

## Generated files

Some committed files are generated. Never edit them by hand.

| Generated file | Source | Regenerate with |
|---|---|---|
| `Resources/widget.html` | `apps/widget/` | `make widget` |
| `Tokens.generated.swift`, `tokens.generated.css`, `widget-tokens.generated.js`, `widget-themes.generated.ts` | `design-system/tokens.json` | `bun run tokens` |
| `Resources/AppIcon-Dev.icon` | `Resources/AppIcon.icon` | `make icons` |
| `Core/SponsorConfig.generated.swift` | `.github/FUNDING.yml` | `make sponsor-config` |
| `apps/streamdeck/com.mrdemonwolf.wolfwave.sdPlugin/imgs/` | `assets/logo-mono.svg` and `apps/streamdeck/src/keyart.ts` | `bun run --filter streamdeck icons` |
| `Resources/Assets.xcassets/About-AppIcon*.imageset/` | `Resources/AppIcon.icon`, `Resources/AppIcon-Dev.icon` | `bash scripts/generate-about-icons.sh` (needs full Xcode) |

Commit the regenerated output with your source change. `make check-drift` runs CI's drift check locally for the first four rows.
CI checks the Stream Deck icons in its own job. No drift check covers the About icons, so regenerate them whenever either app icon changes.
The widget pipeline is covered on the [OBS Widget](/docs/widget#dev-loop) page.

## Edit the docs site

The site lives in `apps/docs`: Next.js as a static export, with [Fumadocs](https://fumadocs.dev) for the docs. Pages are MDX files in `apps/docs/content/docs/`.

### Add a page

1. Create `content/docs/<slug>.mdx`. Its URL is `/docs/<slug>`. Fill in `title`, a `description` of 50 to 160 characters, and the social card fields (`ogTitle`, `ogDescription`, `ogEyebrow`, `ogChips`, `keywords`). `metaTitle` changes only the browser title.
2. List it in `content/docs/meta.json` under its group. Groups are the `---Name---` separators.
3. Give it a sidebar tile in `lib/docs-nav.ts` (`DOCS_NAV_ENTRIES`): an icon, a tint, and an optional shorter label.

`bun run --filter docs test` fails if a page in `meta.json` has no tile, or a group belongs to no tab.

### Tabs and tiles

The sidebar has three tabs: **Guides**, **Developers**, and **Design**. `DOCS_TABS` in `lib/docs-nav.ts` lists which `meta.json` groups each tab holds, and `lib/docs-tree.ts` builds the tabbed sidebar from them. Files never move into folders, so URLs, anchors, and every hard-coded `content/docs/*.mdx` path stay put.

A tile's color says what the page is about: `brand` for WolfWave itself, a partner color for a service (`twitch`, `discord`, `apple-music`, and `graphite` for OBS and Stream Deck), `gray` for general and legal pages, `red` for fixes, `indigo` for contributor docs, and `wolfwave` for the design system.

### Formatting that renders specially

- **UI paths.** Write a path as one bold run, with spaces around each arrow: `**Settings → Twitch → Bot Commands**`. It renders as a path chip, with a gear in front of Settings. Keep links, code, and other bold out of it.
- **Troubleshooting entries.** Paragraphs that start with `**Message:**`, `**Why:**`, and `**Fix:**` render as one framed list. A list or table right after a label joins it.
- **Diagrams.** A `` ```mermaid `` fence renders as a diagram in the browser.

All three come from `lib/rehype-docs.ts`. They run after the markdown is captured, so `llms.txt`, the per-page markdown, and search keep the plain source.

### Anchors are a contract

The native app opens `/docs/troubleshooting#<id>` from its error banners, and the README, the app, and other pages link to headings across the site. Don't rename a linked heading. To change its words, keep the old anchor with an explicit id: `## New title [#old-id]`. Give new troubleshooting sections an explicit `[#id]` too.

### Components

Fumadocs' components (`Callout`, `Cards` and `Card`, `Steps`, `Tabs`, `Accordions`, `Files`) work in any page. The docs home uses `HomeHero`, `MenuMap`, `SetupPath`, and `LinkList` from `components/docs/home.tsx`. Styles live in `app/docs/docs.css`, which only docs pages load, so the landing page never sees them.

## Open a pull request

1. Branch off `main`. One concern per PR.
2. Run `make test` and the [lint gates](#lint-gates).
3. Fill in the [PR template](https://github.com/MrDemonWolf/wolfwave/blob/main/.github/PULL_REQUEST_TEMPLATE.md) checklists.
4. User-facing change? Add a one-line bullet to `CHANGELOG.md` under the top `## [x.y.z]` heading, and to the top block of [`changelog.mdx`](/docs/changelog). Keep each bullet on one line and start it with `-`. `make lint-sync` renders the real changelog and fails on nested, indented, wrapped, or `*` bullets.
5. Contributor-only change? Put it under `### Developer` in `CHANGELOG.md`. It skips the in-app notes and the docs changelog.
6. Update the docs your change touches (`features`, `settings`, `bot-commands`, `architecture`).
7. Attach a screenshot or recording for any UI change.

Don't bump `CURRENT_PROJECT_VERSION`. CI sets the build number from `scripts/version.sh`.

More detail: [`CONTRIBUTING.md`](https://github.com/MrDemonWolf/wolfwave/blob/main/CONTRIBUTING.md) and [`CLAUDE.md`](https://github.com/MrDemonWolf/wolfwave/blob/main/CLAUDE.md).

## Rich Presence art assets (fork maintainers)

Rich Presence shows three images registered on the Discord app. They are **not** bundled with WolfWave.

| Asset name | Shown when |
|---|---|
| `apple_music` | Fallback large image, and the small badge while playing |
| `pause` | Small badge while paused |
| `wolfwave` | Large image on the song-less idle status (the default **When music stops** choice, "Listening to WolfWave") |

Discord shows no image for a name that isn't uploaded.

Shipping a fork with your own `DISCORD_CLIENT_ID`?

1. Open your Discord app's **Rich Presence → Art Assets** page.
2. Upload `apple_music.png`, `pause.png`, and `wolfwave.png` from [`discord-assets/`](https://github.com/MrDemonWolf/wolfwave/tree/main/discord-assets). Name each asset after its file, without `.png`, in exact lowercase.
3. Wait about 10 minutes for Discord's CDN.

## Production build

```bash
make prod-build
```

- The DMG lands at `builds/WolfWave-{version}.dmg`.
- It builds Apple Silicon (`arm64`) only, like the shipped app.
- With a Developer ID Application certificate in your Keychain, the app is re-signed for distribution (inside-out, via `scripts/codesign-app.sh`, the same script CI uses).
- `make prod-install` builds and copies the app to `/Applications`.
- The DMG background comes from `scripts/generate-dmg-background.swift`. Regenerate with `swift scripts/generate-dmg-background.swift assets` and commit the PNGs.

### Notarization

```bash
APPLE_ID=you@example.com \
APPLE_TEAM_ID=YOUR_TEAM_ID \
APPLE_APP_PASSWORD=xxxx-xxxx-xxxx-xxxx \
make notarize
```

- `make notarize` signs, submits, and staples the DMG.
- It then runs `stapler validate` and `spctl --assess`, so a bad ticket fails here, not on a user's Mac.
- `make verify-notarize` reruns those two checks on an existing DMG.

<Callout type="info">
  Create an app-specific password at
  [appleid.apple.com](https://appleid.apple.com/account/manage) under **Sign-In and
  Security → App-Specific Passwords**.
</Callout>

## CI/CD

| Workflow | When it runs | What it does |
|---|---|---|
| `test.yml` (CI) | Every push to `main` and every pull request | Unit tests, drift checks, widget tests, UI tests, docs build and tests, Stream Deck plugin, SwiftLint, crash-safety, headers, sync, design-system lint |
| `build_release.yml` | `v*` tag push, or a manual run | Runs the unit tests, then (after approval in the `release` environment) builds, signs, notarizes, embeds release notes in the Sparkle appcast, and uploads the DMG to a **draft** GitHub Release |
| `update_homebrew.yml` | After a release is published | After approval in the `homebrew-tap` environment, opens a PR bumping the Homebrew cask |
| `docs.yml` | Pushes to `main` that change the docs, the design system, or JS tooling, or a published stable release | Deploys this site to GitHub Pages |
| `nightly.yml` | Daily at 05:00 UTC | Signed build off `main` for the [Nightly channel](/docs/nightly). Skipped when nothing that ships changed |
| `dependency-review.yml` | Every pull request | Fails a PR that brings in a dependency with a known vulnerability of moderate severity or higher |
| `license-year.yml` | Every January 1 | Opens a PR that updates the copyright year in About and `Info.plist` |
| `update_sponsors.yml` | Daily at 00:00 UTC | Opens a PR that refreshes the sponsors image. Skipped on forks, and when `SPONSORKIT_TOKEN` is missing |

How `test.yml` behaves:

- Each job runs only when its files change, so a docs-only PR skips the native jobs.
- **Required Checks** is the aggregate gate. It passes only when every job whose files changed succeeded and every other job was skipped.
- **Xcode Compatibility** builds with the newest Xcode. It is informational and never blocks.
- The docs job runs the type check, lint, a full build, and the docs tests, including the SEO guard.
- A change to `StreamDeckCommand.swift`, `AppConstants.swift`, or `WebSocketAuthToken.swift` re-runs the Stream Deck job, so a protocol mismatch fails the PR.

Dependabot is not a workflow. `.github/dependabot.yml` opens grouped weekly PRs for GitHub Actions, SwiftPM, and bun.
CI, Release, and Nightly share one build setup, `.github/actions/setup-native-build` (bun, the generated widget and tokens, a generated `Config.xcconfig`, SponsorConfig, and the SwiftPM cache), and one test command, `make test-ci`.

### Required GitHub secrets

| Secret | What it is |
|---|---|
| `TWITCH_CLIENT_ID` | Twitch application Client ID |
| `DISCORD_CLIENT_ID` | Discord application ID |
| `DEVELOPER_ID_CERT_P12` | Base64 Developer ID certificate |
| `DEVELOPER_ID_CERT_PASSWORD` | Password for that certificate |
| `APPLE_ID` | Apple ID for notarization |
| `APPLE_TEAM_ID` | Apple Developer Team ID |
| `APPLE_APP_PASSWORD` | App-specific password for notarization |
| `SPARKLE_PRIVATE_KEY` | EdDSA key that signs the appcast |
| `PROVISIONING_PROFILE_B64` | Optional. Developer ID profile with iCloud, for "Sync with iCloud" |
| `HOMEBREW_TAP_TOKEN` | Token that can push a branch and open a PR on the Homebrew tap, for `update_homebrew.yml` |
| `SPONSORKIT_TOKEN` | Optional. GitHub token for `update_sponsors.yml`. Without it, the sponsor refresh skips itself |

### Cutting a release

Before you tag:

1. Bump every `MARKETING_VERSION` in `apps/native/WolfWave.xcodeproj/project.pbxproj`. Leave `CURRENT_PROJECT_VERSION` alone.
2. Add the `## [X.Y.Z] - YYYY-MM-DD` entry to `CHANGELOG.md`, and the matching `## vX.Y.Z. Month DD, YYYY` entry to [`changelog.mdx`](/docs/changelog).

Then push a tag that matches `MARKETING_VERSION`. A mismatch fails the workflow. So does a tag on a commit that isn't later than the last nightly's, because Sparkle would never offer that release to Nightly testers.

```bash
git tag vX.Y.Z
git push origin vX.Y.Z
```

1. The workflow runs the unit tests, then waits for manual approval in the `release` environment.
2. It uploads to a draft release. Rerunning updates the draft; it never replaces a published release.
3. Review the draft and publish it.
4. Publishing starts the Homebrew cask PR (it waits for approval in the `homebrew-tap` environment) and a docs redeploy.
5. Right after the release lands, bump `MARKETING_VERSION` to the next version, open a new `## [X.Y.Z] - Unreleased` block in both changelogs, and move the example nightly version in `nightly.mdx`. Until you do, every nightly claims the version you just shipped.

To rehearse, run the workflow by hand with `dry_run` on. It runs everything except the draft release.

The full list is the [Release Checklist](https://github.com/MrDemonWolf/wolfwave/blob/main/CLAUDE.md#release-checklist).
